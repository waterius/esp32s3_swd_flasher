## Context

Зачем — `proposal.md`, что должно получиться — спеки `swd-flash`, `gdb-server` и `target-log`.
Здесь только то, что задаёт способ. Первоисточники перечислены в реестре `datasheets/README.md`
(задача 1.1):
- RM — PY32F002B-C Reference Manual V1.0;
- DS — PY32F002B Datasheet V1.0;
- пак Puya `PY32F0xx_DFP` 1.1.7: `Flash/PY32F002Bxx/FlashPrg.c` и `.pdsc`;
- руководство GDB, приложение «Remote Protocol»: пакеты, карта памяти, описание регистров;
- ядро Arduino-ESP32 3.3.12 (из pioarduino `55.03.312-1`): `cores/esp32/USBCDC.cpp`;
- Black Magic Debug: `src/target/puya.c` (BSD-3-Clause) и PR #2000 с поддержкой PY32F002B —
  эталон для сверки записи и таймингов; код под GPL из BMP не копируем.

- **Память PY32F002B:**
  - основная flash — 24 КБ с `0x08000000`, страница 128 Б (192 страницы), сектор 4 КБ;
  - USER OTP — одна страница 128 Б по адресу `0x1FFF0280`. Стирается и пишется как основная
    flash, полное стирание её не трогает. `0xAA55` в битах 15:0 слова 0 после POR запирает её
    навсегда: ни стереть, ни записать (RM §3.4, §4.5.8, табл. 4-6 и 4-7). Защита записи (WRP) на
    OTP не действует (RM §4.6.2);
  - ОЗУ — 3 КБ с `0x20000000`.
- **Алгоритм записи PY32F002B** (`FlashPrg.c`, RM §4.2.3):
  - разблокировка: `FLASH_KEYR` ← `0x45670123`, `0xCDEF89AB`. Любая неверная
    последовательность запирает `FLASH_CR` до сброса и даёт ошибку шины (RM §4.2.3.1). Пак
    разблокирует в `Init` один раз на сеанс записи;
  - стирание страницы: `FLASH_CR |= PER | EOPIE`, запись любого слова по адресу страницы,
    ожидание `BSY`, снять `PER`;
  - запись страницы: `FLASH_CR |= PG | EOPIE`, 32 слова подряд, `PGSTRT` перед последним
    словом, ожидание `BSY`, снять `PG`. Запись только сбрасывает биты в 0: результат — И старого
    и нового;
  - флаг `EOP` ставится только при `EOPIE` (RM §4.8.4); RM советует его проверять (§4.2.3.2 п. 9,
    §4.2.3.3 п. 6). В `FlashPrg.c` проверка `EOP` после стирания и записи страницы
    закомментирована (строки 339–342, 414–417, 541–544), осталась только в `EraseChip`.

  Время (DS табл. 5-15): запись страницы 1,0 мс (макс. 1,5), стирание страницы или сектора
  3,5 мс (макс. 5,0).
- **Тайминги flash PY32F002B.** Длительность стирания и записи задают девять регистров
  `FLASH_TS0`, `TS1`, `TS2P`, `TPS3`, `TS3`, `PERTPE`, `SMERTPE`, `PRGTPE`, `PRETPE` — в тактах HSI
  (RM §4.8.11–4.8.19):
  - RM велит перед записью загрузить в них заводские значения для текущей частоты HSI из
    информационной области, «иначе операция не удастся» (§4.2.3.6). Для 24 МГц это пять слов
    `0x1FFF011C`–`0x1FFF012C`, раскладка полей — RM §4.5.2–4.5.6;
  - значения после сброса — номинал для 24 МГц: `PERTPE` `0x14820` = 84 000 тактов = 3,5 мс,
    `PRGTPE` `0x5DC0` = 24 000 тактов = 1,0 мс, как в DS;
  - частота HSI — `RCC_ICSCR.HSI_FS` (биты 15:13). Регистр сбрасывается только по POR/BOR
    (RM §8.6.2): частоту, которую выставила прошивка платы, NRST не отменяет. DS описывает только
    HSI 24 МГц. RM сам себе противоречит: подпись поля — «100 — 24 МГц», значение после сброса —
    `0x00FF10FF`, то есть `HSI_FS` = 000. Код частоты 24 МГц для этого кристалла лежит в заводском
    слове `HSI_TRIMMING_FOR_USER` по `0x1FFF0100` (RM §4.5.1): его и записывают в `RCC_ICSCR`,
    чтобы включить 24 МГц;
  - пак Puya тайминги не трогает (`InitRccAndFlashParam` пустая) и полагается на значения после
    сброса. Black Magic Debug для PY32F002A загружает их из информационной области, его PR #2000
    для PY32F002B — значения для 24 МГц.
- **Защита записи** задаётся option bytes (`FLASH_WRPR`, `FLASH_SDKR`, `FLASH_BTCR`; RM §4.6,
  §4.8). Попытка записи в защищённое даёт `WRPERR` или молча игнорируется; второе ловит сверка.
- **Другие чипы.** В паке Puya есть исходники алгоритмов и для остальных PY32F0xx
  (`Flash/PY32F0xx/FlashPrg.c` — F002A, F003, F030; `Flash/PY32F072xx/FlashPrg.c`). Их
  контроллер другой: `InitRccAndFlashParam` там настраивает HSI и тайминги flash. Сейчас эти
  чипы не нужны (владелец, 2026-11-11).
- **Готовые решения** (поиск 2026-11-12):
  - Black Magic Debug — gdb-сервер в самом программаторе, тот же протокол. Драйвер Puya
    (`puya.c`, BSD-3-Clause; ядро BMP, `cortexm.c`, — GPL-3.0). В основной ветке PY32F002B нет:
    драйвер принимает `DBG_IDCODE` `0x06188061` (F07x) или с нулевыми младшими 12 битами, а у
    F002B `0x20200061`. PR #2000 добавляет F002B, в основную ветку не влит. OTP, `DBGEN` и
    `DBG_IWDG_STOP` драйвер не трогает; разблокирует один раз на запись и ставит `LOCK` в конце;
    `EOP` не проверяет; `BSY` ждёт без предела. Подключение под сбросом — в `cortexm.c`;
  - BMP на ESP32 — официальной платформы нет. Порт на ESP32-S3 (litui) не доделан, последнее
    изменение 2024-02; порт Flipper на ESP32-S2 — GPL-3.0, 2024-06; порт для Cardputer на
    ESP32-S3 — два CDC-порта;
  - ESP32 с веб-страницей шьют по SWD nRF52 (`atc1441/ESP32_nRF52_SWD`) и STM32F4 (Airfrog), без
    PY32 и PlatformIO;
  - из браузера шьют через WebUSB и CMSIS-DAP (DAP.js, FreeOCD WebDebugger, micro:bit MakeCode)
    — другой путь для страницы, решается в её change'е.
- **Отладка PY32F002B:**
  - `DBG_IDCODE` — `0x40015800`, после сброса `0x20200061` (RM §22.9.1). Серийные
    PY32F002BF15U6 на платах приставки отдают `0x20220064` (waterius.node, 2026-10-02; оснастка,
    2026-11-12) — описание чипа принимает оба;
  - `DBG_CR` — `0x40015804`, `DBG_STOP` — бит 1; сбрасывается только по POR (RM §22.9.2);
  - `DBG_APB_FZ1` — `0x40015808`, `DBG_IWDG_STOP` — бит 12 (RM §22.9.3);
  - тактирование модуля DBG — `RCC_APBENR1.DBGEN`, бит 27 по адресу `0x4002103C`, после сброса 0
    (RM §8.6.14). Пак включает его перед записью в `DBG_*` (последовательность `DebugCoreStart`
    в `.pdsc`);
  - UID — 16 Б с `0x1FFF0000` (RM §4.3);
  - `IDCODE` порта отладки в RM указан двояко — `0x0BB11477` (§22.4.3) и `0x0BC11477`
    (§22.4.5).
- **Option bytes, которые выключают отладку.** `NRST_MODE` делает PC0 обычной ногой вместо NRST,
  `SWD_MODE` переносит SWDIO на PC0 (RM §4.4.1, OPTR биты 14:13; DS, примечание к табл. 3-2).
  `IWDG_SW = 0` включает IWDG аппаратно с самого сброса (RM §4.4.1, §18.3.2).
- **Спящий чип.** В Stop без `DBG_STOP` чип по SWD не отвечает. Прошивка, которая быстро
  засыпает и `DBG_STOP` не ставит, оставляет отладчику миллисекунды после сброса. Подключение с
  опросом раз в десятки миллисекунд в такое окно не попадает.
- **Ядро после остановки на сбросе.** `DHCSR` и `DEMCR` сбрасываются только по POR (RM §22.5):
  `C_DEBUGEN`, `C_HALT` и `VC_CORERESET` переживают NRST. Остановка `VC_CORERESET` происходит,
  когда ядро уже взяло SP и адрес старта из таблицы векторов. Если потом переписать flash и
  просто отпустить ядро, оно пойдёт по адресу старта старой прошивки. Новую прошивку запускает
  только новый сброс. Чтение `DHCSR` сбрасывает флаг `S_RESET_ST`.
- **Ноги PY32F002B:** SWCLK — PA2, SWDIO — PB6, NRST — PC0 (DS табл. 3-2). Прошивка платы вправе
  забрать PA2 и PB6 под свои функции (RM §22.2.2): у PB6 есть SPI_MISO и ADC_IN6, у PA2 —
  I2C_SCL. Питание чипа 1,7–5,5 В, вход ноги — не выше VCC + 0,3 В (DS табл. 5-1). Ток ноги — до
  20 мА (DS табл. 5-2). TX лога у каждой платы свой.
- **Оснастка:** ESP32-S3 Super Mini — ESP32-S3, 4 МБ flash, USB на самом чипе, RGB-светодиод на
  GPIO48. GPIO1, 2, 4, 5 выведены на гребёнку (владелец, 2026-11-11). Логика 3,3 В, ноги не
  выдерживают 5 В.
- **USB CDC в Arduino-ESP32 3.3.12** (`USBCDC.cpp`):
  - `Serial` (`operator bool`, событие CONNECTED) считает порт открытым, только когда подняты и
    DTR, и RTS. Сам DTR — `tud_cdc_n_get_line_state()` TinyUSB; `write()` при упавшем DTR
    сразу возвращает 0;
  - `reboot_enable` по умолчанию включён: последовательность линий DTR/RTS, как у esptool, или
    скорость 1200 в line coding перезагружают ESP в ROM-загрузчик;
  - при `setTxTimeoutMs(0)` `write()` может принять только часть данных;
  - очередь приёма по умолчанию 256 Б (`setRxBufferSize`), лишние байты теряются.
- **PlatformIO и gdb.** Платформа `py32f0` при `upload_protocol = blackmagic` запускает gdb из
  `toolchain-gccarmnoneeabi` (сейчас gdb 15.2, Arm GNU Toolchain 14.2.Rel1):
  `-nx --batch -ex "target extended-remote $UPLOAD_PORT" -ex "monitor swdp_scan" -ex "attach 1"
  -ex "load" -ex "compare-sections" -ex "kill" <elf>` (`builder/main.py`). Без `upload_port`
  PlatformIO ищет только Black Magic Probe по VID:PID `1D50:6018` (`platformio/device/finder.py`)
  и оснастку не найдёт. Префикс `\\.\` он добавляет только найденному порту.
- **Что делает gdb 15.2 на самом деле** — записано заглушкой протокола на ПК, 2026-11-12, и
  повторено ревью (это модель, не Black Magic Probe; на плате проверяется задачами 8.x):
  - первый байт gdb — `+`; затем `qSupported`, `vCont?`, `vMustReplyEmpty`, `QStartNoAckMode`,
    `!`, `Hg0`, `qXfer:features:read:target.xml`, `qTStatus`, `?`. Байт `-` от оснастки до
    ответа на `qSupported` срывает подключение: «Protocol error: QStartNoAckMode (noack)
    conflicting enabled responses», код 1. Текст без `-` и `$` gdb переносит;
  - `monitor swdp_scan` — `qRcmd`; `attach 1` — `vAttach;1`, затем `qC`, `Hg1`, снова
    `target.xml`, `g`, `qOffsets`, `qSymbol::`, `qfThreadInfo`/`qsThreadInfo`,
    `qXfer:memory-map:read`, `m` у адреса PC;
  - `load` ELF прошивки: один `vFlashErase` на весь диапазон секций, округлённый до блока карты
    памяти (секции `0x08000000`–`0x08004D58` → `vFlashErase:08000000,00004d80`), затем
    `vFlashWrite` по секциям и кускам не больше `PacketSize`, `vFlashDone`, затем `P` — PC
    на точку входа. Байты стёртых блоков, которых нет в секциях, gdb не дописывает: они
    остаются стёртыми. Два `load` в сеансе — у каждого свой `vFlashErase` … `vFlashDone`;
  - `load` файла Intel HEX gdb разбирает сам (BFD `ihex`): 128 Б на `0x1FFF0280` →
    `vFlashErase:1fff0280,00000080`, один `vFlashWrite`, `vFlashDone`;
  - секция хоть частично вне карты памяти — gdb сам пишет `Load failed` и не шлёт ни одного
    `vFlash*`. Если потом `kill` получил `OK`, код 0;
  - `compare-sections` сначала пробует `qCRC`, без него сверяет чтением `m`. Расхождение —
    только предупреждение, на код возврата не влияет;
  - ошибка на `vFlashDone` — gdb пишет `Error finishing flash operation` и идёт к следующей
    команде. После ошибки на `vFlashErase` `vFlashDone` не приходит. Текст ошибки (`E.<текст>`)
    gdb не показывает. Код возврата `--batch` — по последней команде. Ошибка на `vKill` —
    `Can't kill process`, код 1, затем gdb шлёт `D`. `detach` с `OK` — код 0;
  - после неудачных `monitor swdp_scan` и `attach` gdb всё равно шлёт `vFlash*`; если оснастка
    отвечает на них `OK`, gdb падает с внутренней ошибкой (`inferior_thread`), код 134;
  - чтение и запись вне карты памяти gdb отвергает сам («Cannot access memory»), к оснастке не
    обращаясь;
  - `continue` с ответом `E01` — «Remote failure reply: E01», «Program stopped.»

## Goals / Non-Goals

**Goals:**
- Чип выбирается аргументом (`chip <имя>`). Всё, что зависит от чипа, собрано в его описании,
  остальное от чипа не зависит. Описание одно — `py32f002b`.
- PlatformIO шьёт через оснастку штатно, gdb пишет и USER OTP. Всё — через один USB-порт.
  Провал заливки виден по коду возврата.
- Оснастка подключается к спящему PY32F002B и пишет образ в основную flash и USER OTP по
  правилам спеки `swd-flash`.
- Вне сеанса SWD оснастка не мешает плате, в том числе после брошенного сеанса.
- Решения «что писать, что пропустить, от чего отказаться», порядок записи, режимы порта и
  разбор пакетов gdb проверяются тестами на ПК.
- Узнать, какой способ подключения работает: под сбросом или сразу после.
- Измерить время шагов и полное время на плату.

**Non-Goals:**
- Другие чипы и запуск FLM.
- Отладка: продолжение, шаги, точки останова, запись в ОЗУ — отдельный change.
- Универсальная страница в браузере и полное стирание основной flash — следующий change этого
  репозитория; страницы изделий — в их репозиториях.
- Хранение образа в оснастке.
- Питание платы от оснастки и проверка платы.
- Запись option bytes, снятие защиты.
- Ускорение записи секторами: сначала замер (§8).

## Ограничения, заметные человеку

- **Напряжение.** Плата должна питаться от 3,0–3,6 В. При другом питании нужен преобразователь
  уровней: 3,3 В оснастки на плате с питанием 1,8 В превышают допустимое на входе, а 5 В с платы
  повредят ESP32-S3.
- **Option bytes.** Если в них `NRST_MODE` или `SWD_MODE` уводят NRST и SWD на другие ноги,
  оснастка к чипу не подключится и сообщит «чип не отвечает».
- **HSI платы не 24 МГц** — отказ «HSI не 24 МГц: снимите питание платы». Частоту, которую
  выставила прошивка платы, NRST не сбрасывает, а снятие питания — сбрасывает.
- **`upload_port` обязателен.** Сам PlatformIO оснастку не найдёт. `COM10` и дальше на Windows
  пишутся как `\\.\COM10` (проверяется задачей 8.3).
- **Задетая страница — целиком.** Байты страницы, которых нет в образе, после записи — `0xFF`.
  Файл для OTP короче 128 Б стирает остаток страницы.
- **Защищённые страницы.** Оснастка остановится на первой защищённой странице, страницы до неё
  уже переписаны. Снимать защиту она не умеет.
- **Обрыв питания посреди записи** оставляет плату недописанной — залить ещё раз. Обрыв посреди
  записи OTP может оставить в слове 0 любые промежуточные биты. Совет: держать биты 15:0 слова 0
  OTP равными `0xFFFF`, тогда замок не возникнет и при обрыве.
- **Причина провала — в мониторе порта.** gdb пишет только `Error finishing flash operation` или
  `Can't kill process`, а что случилось, оснастка выводит строкой `# ` после сеанса.
- **Сеанс только для чтения закрывать `detach`.** `kill` без удачной записи отвечает ошибкой —
  так PlatformIO видит провал (§9).
- **Отладки нет.** `continue`, шаги и точки останова gdb получит с ошибкой.
- **Сеанс gdb без пакетов 60 с** завершается, плата запускается.
- **`info` перезапускает плату:** это короткий сеанс SWD.
- **`baud`** действует до перезапуска оснастки. Скорость, заданная монитору ПК, на лог не
  влияет.
- **На macOS** порт может открыть второй процесс: открытый монитор во время заливки делит байты
  с gdb. Монитор перед заливкой закрыть.
- **Открытие порта на скорости 1200** перезагружает оснастку в загрузчик ESP.
- **Оснастка потеряла питание посреди сеанса**, а плата питается сама — ядро платы стоит после
  каждого сброса, пока на плате не пропадёт питание или не выполнится `info`.
- **Нужен PlatformIO** или хотя бы gdb из его тулчейна — до change'а со страницей.

## Decisions

### 1. PlatformIO, pioarduino, Arduino, один USB-порт

- Платформа — pioarduino `55.03.312-1`, framework `arduino`, плата `esp32-s3-devkitc-1` с явными
  `board_upload.flash_size = 4MB` и `board_build.partitions = default.csv`: у этой платы по
  умолчанию 8 МБ. `CORE_DEBUG_LEVEL=0`: логи ядра не должны попадать в порт, по нему идёт
  протокол gdb.
- **USB — CDC через TinyUSB** (`ARDUINO_USB_MODE=0`, `ARDUINO_USB_CDC_ON_BOOT=1`). Этому режиму
  виден DTR, то есть открыт ли порт на ПК: от этого зависят вывод (§10) и режимы порта (§9).
  - DTR читается через `tud_cdc_n_get_line_state()`, а не `Serial`/`operator bool`: тот ждёт ещё
    и RTS, а gdb на Windows может его не поднять (Context).
  - `setRxBufferSize(8192)` — больше `PacketSize` с кадром (§9).
  - Всё, что оснастка пишет в порт, дописывается в цикле, пока DTR поднят: `write()` может
    принять часть.
  - `reboot_enable` оставлен включённым: им перезаливается сама оснастка (задача 1.2). На плате
    (2026-11-12) DTR/RTS esptool оснастку в загрузчик не переводят, а открытие порта на 1200 —
    переводит; поэтому `board_upload.use_1200bps_touch` и `wait_for_upload_port`: PlatformIO сам
    касается порта оснастки и ждёт порт загрузчика, у него другое имя. Что
    открытие и закрытие монитора и gdb на Windows её не перезагружает, проверяет задача 8.3.
    Перезагружает — выключить и перезаливать оснастку с кнопкой BOOT.
- Выбранный чип — в NVS через `Preferences`. Отметка «идёт сеанс» — в RTC-памяти ESP
  (`RTC_NOINIT_ATTR`): переживает сбой и программный перезапуск оснастки (§5). Файловой
  системы нет.
- Второе окружение `native` — юнит-тесты чистого кода на ПК (§12).
- **Почему Arduino, а не ESP-IDF:** готовые Preferences и USB CDC. SWD Arduino не мешает: ноги
  пишутся напрямую в регистры GPIO.
- **Отвергнуто: ESP-IDF без Arduino** — то же самое, но больше своего кода.
- **Отвергнуто: USB Serial/JTAG** (`ARDUINO_USB_MODE=1`). Им проще перезаливать саму оснастку,
  но открытие порта на ПК ему не видно.
- **Отвергнуто: чужой VID:PID ради автопоиска порта** — оснастка выдавала бы себя за другое
  устройство.

### 2. Провода и ноги

| ESP32-S3 Super Mini | Плата | Как |
|---|---|---|
| GPIO1 | SWCLK (у PY32F002B — PA2) | в сеансе — выход; вне сеанса — вход без подтяжки |
| GPIO2 | SWDIO (PB6) | в сеансе — вход-выход с подтяжкой вверх; вне сеанса — вход без подтяжки |
| GPIO4 | NRST (PC0) | открытый сток: 0 — сброс; отпущен — подтяжка платы |
| GPIO5 | TX лога платы | вход UART1, подтяжка вверх |
| GND | GND | всегда |
| 3V3 | 3V3 | только если у платы нет своего питания |

- **Резисторы 100–330 Ом последовательно** в SWCLK, SWDIO, NRST и линии лога, сила выхода ESP —
  наименьшая (`GPIO_DRIVE_CAP_0`). Если прошивка платы держит ногу SWD выходом, встречный ток в
  начале сеанса ограничен.
- **Вне сеанса SWD** (§5) оснастка не держит ни SWCLK, ни SWDIO, ни NRST: прошивка платы
  пользуется этими ногами как хочет, подтяжка оснастки не искажает её АЦП и ток сна.
- Ноги стоят в одном заголовке `src/pins.h`. Ноги-«ремешки» ESP32-S3 (GPIO0, 3, 45, 46) не
  заняты. Кнопка BOOT и светодиод оснастке не нужны: итог виден на экране ПК.

### 3. SWD — общий; запись PY32F002B — регистрами, без FLM

- **SWD** от чипа не зависит. Ноги дёргаются напрямую через `GPIO_OUT_W1TS/W1TC` и
  `GPIO_ENABLE_W1TS/W1TC`. Протокол — ADIv5:
  - вход: line reset (≥ 50 единиц), `0xE79E` (JTAG → SWD), снова line reset, такты покоя, чтение
    `IDCODE`;
  - включение отладки: `CTRL/STAT = 0x50000000` и ожидание подтверждений;
  - память через AHB-AP: `CSW = 0x23000052` — слова по 32 бита с автоинкрементом адреса, `TAR`,
    `DRW`, чтение через `RDBUFF`. Автоинкремент гарантирован в пределах 1 КБ: на границе `TAR`
    ставится заново;
  - после каждой транзакции — не меньше 8 тактов покоя (RM §22.4.4 требует хотя бы 2);
  - `WAIT` — повтор до 10 мс, потом `ABORT = 0x1F` (с DAPABORT) и ошибка шага; `FAULT` —
    `ABORT = 0x1E` и ошибка шага;
  - после пакета чтений — проверка `CTRL/STAT`: `STICKYERR` означает, что прочитанному верить
    нельзя.
- **Регистры ядра** — общие для Cortex-M: `DCRSR` (`0xE000EDF4`) выбирает регистр, `DCRDR`
  (`0xE000EDF8`) — значение, готовность — `S_REGRDY` в `DHCSR`. Нужны gdb: `g`, `p`, `P` (§9).
- **`S_RESET_ST` копится.** Любое чтение `DHCSR` — опрос `S_HALT`, `S_REGRDY` — сбрасывает этот
  флаг (Context). Поэтому `port/dap` при каждом чтении `DHCSR` запоминает его в отметке сеанса,
  а сеанс проверяет отметку (§8).
- **Частота SWD — одна константа**, по умолчанию около 1 МГц: полупериод отсчитывается тактами
  ESP.
- **Запись PY32F002B — регистрами по SWD, как в `FlashPrg.c`**, а не запуском FLM в ОЗУ чипа.
  - Алгоритм — несколько записей в регистры на страницу.
  - Запуск FLM потребовал бы разбора ELF, загрузки кода в 3 КБ ОЗУ, регистров ядра и точки
    останова. Это втрое больше кода без выигрыша для одного чипа (А5).
  - Цена — своя реализация, которую сверяем с `FlashPrg.c` построчно.
- **Для следующих чипов** способ выбирается в их change'е: регистрами по их `FlashPrg.c` из пака
  или запуском FLM. В обоих случаях меняются только функции записи в описании чипа (§6).
- **Отвергнуто: esp-usb-bridge** (ESP32-S3 как CMSIS-DAP плюс pyOCD на ПК). Он требует pyOCD и
  пак на ПК (БТ/swd-flash-py32f002b/1), а OTP с паком не пишется. Остаётся способом отделить
  ошибку проводов от ошибки нашего SWD, если чип не ответит.
- **Отвергнуто: Black Magic Debug на ESP32-S3** (Context, «Готовые решения»):
  - официальной платформы ESP32 нет, порты заброшены — доделывать и сопровождать пришлось бы
    самим;
  - PY32F002B в основной ветке нет, OTP и правил замка нет;
  - два COM-порта вместо одного;
  - ядро и gdb-сервер под GPL-3.0 — наша прошивка тоже стала бы GPL.

  Что берём у BMP: тот же протокол (§9), а `puya.c` и PR #2000 — эталон для сверки записи и
  таймингов (задача 1.1).

### 4. Подключение — общее для Cortex-M, через NRST, два способа по очереди

1. **Под сбросом:**
   - NRST в 0, вход SWD, `IDCODE`;
   - `DEMCR = VC_CORERESET` (`0xE000EDFC`, бит 0), `DHCSR = 0xA05F0001`;
   - NRST отпустить, ждать `S_HALT`.

   Ядро встаёт на первой инструкции, прошивка платы не выполняет ни такта. RM разрешает
   отладчику писать в `DBG_*` под системным сбросом — довод за этот способ.
2. **Сразу после сброса**, если под сбросом чип молчит:
   - импульс NRST, затем попытки входа подряд без пауз, но не дольше 50 мс;
   - поймав чип: `DHCSR = 0xA05F0003`;
   - затем `VC_CORERESET` и `AIRCR = 0x05FA0004` — перезапуск в остановку на первой инструкции,
     чтобы периферия была в состоянии после сброса. Ошибку ответа на запись `AIRCR` не считаем:
     он может пропасть вместе со сбросом, как в `ResetSystem` CMSIS-Pack.

   Ожидание остановки после NRST и после `SYSRESETREQ` при неудачном чтении входит в SWD заново:
   порт отладки мог сброситься вместе с чипом.

   Вход по SWD — около 100 тактов, доли миллисекунды. Чтобы проверить этот способ на плате, где
   срабатывает первый, сборка с флагом `SWD_CONNECT_AFTER_RESET_ONLY` пропускает первый
   (задача 8.2).

- Регистры `DHCSR`, `DEMCR`, `AIRCR` — общие для Cortex-M, поэтому подключение не зависит от
  чипа. Какой способ сработал, сеанс запоминает и сообщает.
- Ответ — `# SWD: под сбросом` или `# SWD: после сброса`.
- Предел всего подключения — 1 с, потом «чип не отвечает».

**После остановки — функция чипа «подготовить».** У PY32F002B порядок такой:
1. Включить `RCC_APBENR1.DBGEN`, затем прочитать `DBG_IDCODE` — как `DebugCoreStart` пака:
   без тактов модуль DBG может ответить ошибкой шины, а не нулём. Включение тактирования —
   единственная запись до сверки, flash и OTP она не касается.
2. Сверить идентификатор — чистой функцией `core/plan` (§7). Не тот чип — отказ.
3. Запомнить `DBG_APB_FZ1`.
4. `DBG_APB_FZ1 |= DBG_IWDG_STOP` и прочитать обратно. Бит не встал — отказ до записи: при
   аппаратном IWDG чип сбросится посреди прошивки.
5. Прочитать `RCC_ICSCR`, заводское слово «HSI 24 МГц» и пять слов таймингов для 24 МГц,
   проверить функцией «тайминги» из описания чипа (§6): поле `HSI_FS` в `RCC_ICSCR` должно
   совпасть с тем же полем заводского слова. Иначе — отказ «HSI не 24 МГц: снимите питание
   платы» с обоими значениями: NRST частоту не сбрасывает, снятие питания — сбрасывает (Context).
   Сама оснастка частоту не меняет.
6. Прочитать UID.

### 5. Сеанс SWD и его завершение

- **Сеанс** начинается командой `info`, `monitor swdp_scan` или `vAttach`, если сеанса ещё нет.
  Заканчивается:
  - после ответа на `info`;
  - на `vKill` и `D`;
  - при выходе порта из режима gdb (§9);
  - если в режиме gdb нет пакетов 60 с;
  - при старте оснастки, если в RTC-памяти осталась отметка «идёт сеанс»: оснастка сбросилась
    или упала посреди сеанса. Тогда она подключается к чипу и завершает сеанс как обычно.

  Пересылка лога на время сеанса стоит (§10). Ядро весь сеанс стоит: отладки нет.
- **Завершение — при любом исходе сеанса, в том числе после отказа, ошибки и неудачного
  подключения.** Подключение уже могло записать `DEMCR` и `DHCSR`, а их сбрасывает только POR:
  без уборки плата вставала бы на векторе сброса до снятия питания. Поэтому порядок один:
  1. Функция чипа «вернуть» — только то, что `prepare` и запись меняли: `FLASH_CR |= LOCK`, если
     чип опознан; `DBG_APB_FZ1` — как был, пока `DBGEN` ещё включён. `RCC_APBENR1` не трогаем:
     его сбросит NRST.
  2. NRST в 0 на 2 мс: с RC на NRST нога должна успеть дойти до нуля.
  3. Если порт отладки отвечает под сбросом — `DEMCR = 0`, `DHCSR = 0xA05F0000`, проверка
     `C_DEBUGEN` = 0, `CTRL/STAT = 0`.
  4. Очистить приёмник лога, отпустить NRST.
  5. Если под сбросом снять отладку не вышло — до 100 мс ловить чип после сброса и сделать то же
     (вход в SWD заново на каждой попытке). Ядро ждёт: `C_HALT` или `VC_CORERESET` переживают
     NRST (Context).
  6. SWCLK и SWDIO — вход без подтяжки, NRST отпущен, отметка «идёт сеанс» снята. Если в сеансе
     была запись — строка `# сеанс: <мс> мс`. Затем лог всего, что принято после отпускания
     NRST (§10).
- **Почему через сброс, а не просто отпустить ядро:** ядро стоит на адресе старта старой прошивки
  (Context). Отпущенное, оно пойдёт по нему в новой. Сброс заставляет взять адрес заново. Поэтому
  и `detach` перезапускает плату, а не отпускает ядро с места.
- **Отвергнуто: импульс NRST после `DHCSR = 0xA05F0000`.** Тогда ядро успевает выполнить код по
  старому адресу. А импульс может оборвать новую прошивку посреди её собственной записи во
  flash.

### 6. Чип — описание и выбор

- **Описание чипа** — всё, что от чипа зависит (А1: набор чипов меняется, требование владельца
  2026-11-11). Оно делится на две части.
- **Данные и чистые правила** — `core/chip.h` (тип) и `chips/py32f002b_desc.cpp` (значения):
  - имя (`py32f002b`);
  - области памяти: имя, начало, размер, единица стирания, читать ли единицу перед записью и
    проверять ли стирание, вид для карты памяти gdb (`flash` или `ram`);
  - адрес и ожидаемое значение идентификатора, адрес и длина UID;
  - функция «решить про единицу»: по итоговой единице и единице чипа даёт «писать»,
    «пропустить» или «отказ: текст». У PY32F002B это правило OTP из спеки: совпадает →
    пропустить; заперта на чипе → отказ; запирает → отказ;
  - функция «тайминги»: по `RCC_ICSCR`, заводскому слову «HSI 24 МГц» и пяти словам
    информационной области даёт девять значений регистров таймингов или отказ «HSI не 24 МГц»;
  - время стирания и записи единицы по даташиту: типичное и наибольшее.

  Без Arduino, собирается и в окружении `native`.
- **Действия с чипом** — `chips/py32f002b_ops.cpp`:
  - «подготовить» (§4) и «вернуть» (§5);
  - «разблокировать» — ключи, только если `LOCK` = 1: повторные ключи в разблокированный `KEYR`
    могут оказаться неверной последовательностью (Context). Затем запомнить девять регистров
    таймингов и записать в них значения функции «тайминги» — как велит RM §4.2.3.6 и как делает
    Black Magic Debug: после ключей;
  - «запереть» — вернуть регистры таймингов, затем `LOCK`;
  - «стереть единицу», «записать единицу», «перезарядить сторож» (`IWDG_KR = 0xAAAA`, как в
    `FlashPrg.c`).

  Работает через `port/dap`.
- **Второй рубеж от замка OTP.** «Записать единицу» у PY32F002B сама отказывается писать слово
  `0x1FFF0280`, если его младшие 16 бит `0xAA55`, что бы ни решило правило выше.
- **Описание `py32f002b`:**

  | Область | Начало | Размер | Единица стирания | Читать перед записью | Проверять стирание | Для gdb |
  |---|---|---|---|---|---|---|
  | `flash` | `0x08000000` | 24 КБ | 128 Б | нет | нет | `flash`, блок `0x80` |
  | `otp` | `0x1FFF0280` | 128 Б | 128 Б | да | да | `flash`, блок `0x80` |
  | `ram` | `0x20000000` | 3 КБ | — | — | — | `ram`, только для чтения из gdb |

  Идентификатор — `0x40015800` = `0x20200061` или `0x20220064`, UID — `0x1FFF0000`, 16 Б. Тайминги для 24 МГц —
  `0x1FFF011C`–`0x1FFF012C`. Время по DS: стирание 3,5 мс (наибольшее 5,0), запись 1,0 мс
  (наибольшее 1,5).
- **Выбор:**
  - описания собраны в таблице `chips/chips.cpp`;
  - `chip <имя>` ищет имя в таблице и сохраняет его в NVS;
  - при старте оснастка берёт имя из NVS;
  - нет имени или его больше нет в таблице — чип не выбран.
- **Почему чип помнится, а не называется в каждой команде:** штатная команда PlatformIO для
  blackmagic чип не передаёт.
- **Отвергнуто: определять чип сам по идентификатору, без аргумента.**
  - Владелец просил аргумент.
  - У разных производителей идентификатор лежит по разным адресам. Чтение «наугад» по чужому
    адресу на неизвестном чипе может дать ошибку шины.

### 7. Образ, план и запись — чистый код

- **`core/image`** строится по областям выбранного чипа. У каждой единицы стирания — данные,
  битовая маска «байт задан образом» и отметка «велено стереть». На вход — стирание диапазона и
  запись байтов (из `vFlashErase` и `vFlashWrite`, §9):
  - адрес вне областей записи — ошибка с адресом, образ отброшен;
  - `vFlashErase` после ошибки начинает новый образ: gdb после ошибки `vFlashDone` не шлёт
    (Context);
  - повторная запись того же байта — последняя побеждает, как в памяти.

  У `py32f002b` это 193 единицы по 128 Б плюс маски по 16 Б — около 28 КБ ОЗУ ESP.
- **`core/plan`** решает, что делать с каждой единицей. На вход — образ, описание чипа и функция
  «прочитать единицу» (в тестах — поддельная память). Для каждой единицы образа:
  1. Итоговая единица — байты образа, остальное `0xFF`.
  2. Если область требует чтения (OTP) — прочитать единицу чипа один раз.
  3. «Решить про единицу» из описания чипа: писать, пропустить или отказ.

  Результат — список «писать» и «пропущено» или отказ с адресом и текстом. Отказ любой единицы —
  отказ всего плана до первого стирания. Двойное чтение не нужно: прочитанное решает только про
  OTP, а неверное «совпадает» поймает сверка.
- **`core/plan`** ещё сравнивает прочитанный идентификатор чипа с описанием — эту функцию зовёт
  «подготовить» (§4).
- **`core/write`** выполняет план через функции чипа: «разблокировать», «запереть», «стереть
  единицу», «записать единицу», «перезарядить сторож», «прочитать единицу». В тестах —
  поддельный чип: ему можно задать `WRPERR` на адресе, «не стёртую» страницу, запирание
  `FLASH_CR` на повторных ключах.
  1. «Разблокировать».
  2. Для каждой единицы «писать»: стереть; если область требует проверки стирания (OTP) —
     прочитать единицу, и если не все байты `0xFF` — стоп «не стёрлась», ничего не писать;
     записать; перезарядить сторож. Первая неудача — стоп с адресом и причиной, следующие
     единицы не трогаются.
  3. «Запереть» — при любом исходе. Второй `load` в том же сеансе снова разблокирует.
  4. Сверка: каждая единица образа, и записанная, и пропущенная, сравнивается с итоговой;
     первый несовпавший адрес — `ошибка`.
  5. Время каждого шага и каждого стирания и записи единицы — через функцию «часы» (в тестах —
     поддельные). Наименьшее и наибольшее время стирания и записи — в строке шага. Вышло за
     наибольшее по DS из описания чипа — строка-предупреждение `# время записи вне даташита`:
     так видно, что тайминги не те, даже если сверка прошла.
- Сценарии спеки «другой чип», «запись не удалась», «кончается посреди страницы», «защита
  записи», «OTP не стёрлась», «образ с замком», «OTP уже такая», «заперта и
  совпадает/отличается», «адрес option bytes», «данные вне образа» проверяются тестами на ПК.
- **Через `image`, `plan` и `write` не проходят** регистры чипа и биты SWD.

### 8. Порядок прошивки

1. Чип выбран (§6), сеанс начат (§5), «подготовить» (§4) — в том числе сверка чипа. Сеанса нет —
   `vFlash*` получают `E01`, неявного подключения нет.
2. gdb шлёт `vFlashErase` и `vFlashWrite` — `core/image` собирает образ (§7). Адрес вне
   областей — `E01` сразу, сеанс помечен «запись не удалась».
3. `vFlashDone` — план (§7) на реальном чтении единиц через `port/dap`. Отказ — ничего не
   стёрто.
4. `core/write` (§7). У PY32F002B:
   - стирание — `PER | EOPIE`, запись — 32 слова (`PG | EOPIE`, `PGSTRT` перед последним);
   - после каждой операции — `BSY` с пределом 50 мс, `WRPERR` и `EOP` (сбросить записью 1),
     снять `PER` или `PG`. `WRPERR`, нет `EOP` или вышел предел — стоп.
5. Сверка всех единиц образа, проверка `STICKYERR`.
6. Отметка `S_RESET_ST` (§3) — чип сбрасывался во время записи → «сброс во время прошивки»,
   `ошибка`. Отметка проверяется и при стопе на шаге 4: после сброса причина — сброс, а не
   «нет `EOP`».
7. Ответ на `vFlashDone`: `OK` или `E01` (§9). Образ очищен, сеанс продолжается до `kill`.

- **Отвергнуто:**
  - полное стирание — снимает данные изделия вне образа;
  - стирание секторами у PY32F002B — 4 КБ захватывают страницы, которых нет в образе;
  - проверка защиты записи до стирания — новые чипы её не имеют, а снять её оснастка всё равно
    не может; `WRPERR` останавливает запись на первой защищённой странице;
  - стирание OTP, если сверка увидела замок. Замок не возникнет, если его нет в образе и OTP
    стёрта перед записью. Это и проверяют три рубежа: правило (§6), отказ «записать единицу»
    (§6), проверка стирания (§7).
- **Оценка для PY32F002B:**
  - стирание и запись — 4,5 мс на страницу по DS, передача по SWD и сверка — около 2–4 мс;
  - около 6,5–8,5 мс на страницу, вся flash (192 страницы) — 1,3–1,7 с.
- Ускорение на потом: сектор 4 КБ, который образ покрывает всеми 32 страницами, стирать одной
  операцией. Делать, только если замер покажет, что время важно.

### 9. Протокол gdb — как у Black Magic Probe

- **Почему так:** PlatformIO уже умеет `upload_protocol = blackmagic`, gdb лежит в его тулчейне.
  Оснастке хватает отвечать на пакеты, которые шлёт gdb (Context), — ставить ничего не надо.
  Страница в браузере и страницы изделий будут говорить тем же протоколом, второго протокола для
  программ нет.
- **Отвергнуто:**
  - свой протокол и свой загрузчик для PlatformIO — скрипт в каждом проекте платы и второй
    протокол для страницы;
  - CMSIS-DAP (esp-usb-bridge) — pyOCD и пак на ПК, OTP не пишется (§3).
- **Режимы порта** — в `core/console`, на вход байты из USB и DTR:
  - порт закрыт (DTR опущен) — вывод копится (§10);
  - DTR поднялся — «не ясно, кто там», вывода нет. Первый входящий `+` или `$` — gdb, порт в
    режиме gdb. Другой байт — человек, порт в текстовом режиме, этот байт — начало строки. 250 мс
    тишины — монитор, текстовый режим, вывод разрешён;
  - текстовый режим: одиночные `+` и `-` вне строки пропускаются, строка выполняется по CR или
    LF, эха нет (в мониторе — `monitor_echo = yes`). `$` начинает возможный пакет: пакет с
    верной контрольной суммой — порт в режиме gdb, иначе накопленное — обычная строка;
  - режим gdb: до `QStartNoAckMode` на каждый пакет — `+` (на неверную сумму — `-`); `+`, `-` и
    Ctrl-C (`0x03`) от gdb пропускаются — ядро и так стоит;
  - обратно в текстовый: после ответа на `vKill` или `D` — но вывод ждёт, пока порт закроют или
    человек пришлёт байт: gdb ещё держит порт; при падении DTR; при любом другом байте вне
    пакета — это начало строки человека. Сеанс SWD при этом завершается (§5);
  - 60 с без пакетов в режиме gdb — сеанс завершается (§5), порт остаётся занятым до падения DTR
    или байта человека.
- **Пакеты и ответы:**

  | Пакет | Ответ |
  |---|---|
  | `qSupported` | `PacketSize=1000;qXfer:memory-map:read+;qXfer:features:read+;QStartNoAckMode+` |
  | `QStartNoAckMode`, `!`, `Hg…`, `Hc…`, `qSymbol::` | `OK` |
  | `?` | `W00` без сеанса, `T05` в сеансе |
  | `qRcmd,<hex>` | вывод команды (§11) пакетами `O<hex>`, затем `OK` |
  | `vAttach;1` | начать сеанс, если его нет (§5); `T05` или `E01` |
  | `qC`, `qfThreadInfo`, `qsThreadInfo`, `qAttached` | `QC1`, `m1`, `l`, `1` |
  | `qXfer:features:read:target.xml` | описание регистров Cortex-M: `org.gnu.gdb.arm.m-profile`, r0–r12, sp, lr, pc, xpsr |
  | `qXfer:memory-map:read` | карта из областей чипа (§6) |
  | `g`, `p<n>`, `P<n>=<v>` | регистры ядра через `DCRSR`/`DCRDR` (§3); без сеанса — `E01` |
  | `m<адрес>,<длина>` | память по AHB-AP; ошибка шины или `STICKYERR` — `E01`; без сеанса — `E01` |
  | `vFlashErase`, `vFlashWrite` | в `core/image`; вне областей или без сеанса — `E01` |
  | `vFlashDone` | запись по §8; `OK` или `E01`; без сеанса — `E01` |
  | `vKill;1` | завершить сеанс (§5); `OK`, только если в сеансе была удачная запись образа и не было неудачной, иначе `E01` |
  | `D` | завершить сеанс, если он есть (§5); `OK` |
  | `c`, `s`, `vCont;…`, `Z…`, `M…`, `X…` | `E01`: отладки нет |
  | остальные (`vCont?`, `vMustReplyEmpty`, `qTStatus`, `qOffsets`, `qCRC` и др.) | пустой ответ: «не поддержано» |

- **Провал записи виден PlatformIO.** gdb после ошибки идёт дальше, а код возврата — по
  последней команде, `kill` (Context). А если образ не помещается в чип, оснастка вообще не
  видит записи: gdb сам пишет `Load failed`. Поэтому `vKill` отвечает `OK`, только если в сеансе
  была удачная запись и не было неудачной. Сеанс без записи закрывают `detach`. Плата
  запускается в любом случае: сеанс завершён.
- **`qCRC` не делаем:** `compare-sections` без него читает память `m` — 24 КБ, доли секунды
  (А5).
- **`PacketSize = 0x1000`** — 4 КБ буфер пакета; прошивка на 24 КБ — шесть-семь пакетов.
- **Проект платы** (README):
  ```ini
  upload_protocol = blackmagic
  upload_port = COM5            ; обязателен; macOS: /dev/cu.usbmodem…; COM10 и дальше: \\.\COM10
  ```
  USER OTP — той же командой gdb из тулчейна, своим файлом:
  `arm-none-eabi-gdb -nx --batch -ex "target extended-remote COM5" -ex "monitor swdp_scan"
  -ex "attach 1" -ex "load otp.hex" -ex "kill"`. Прочитать память — `x/…`, затем `detach`.
  Проект платы может сделать из этого свою цель PlatformIO; оснастке её знать не нужно.
- **`core/gdb` чистый:** работает через функции «цели» — начать и закончить сеанс, прочитать
  память, регистры, записать образ, выполнить команду. На плате их даёт `port/session`, в тестах —
  поддельная цель. Тесты прогоняют сырые байты, записанные с gdb из тулчейна на нейтральном
  образе, вместе с `+` (задача 1.6).

### 10. Лог платы и вывод в порт

- UART1 оснастки, приём на GPIO5 с подтяжкой, 8N1, по умолчанию 115 200, буфер приёма 4 КБ.
  `baud <N>` (1 200–2 000 000) меняет скорость до перезапуска оснастки.
- Байты лога идут в порт как есть. Свои строки оснастка начинает с `# ` с начала строки: если
  лог платы оборвался посреди строки, перед строкой оснастки — CR LF. По этим строкам будет
  разбирать вывод и страница в браузере.
- **Во время сеанса SWD** пересылка стоит: ядро стоит или плата в сбросе, TX платы плавает. В
  конце сеанса приёмник очищается до отпускания NRST (§5).
- **Вывод в порт** — в `core/console` (§9). Он идёт, только когда порт свободен: открыт на ПК
  (DTR), известно, что на том конце человек или монитор, и порт не занят gdb. Иначе строки
  оснастки и лог копятся в буфере: первые 4 КБ, остальное считается и отбрасывается. Когда порт
  свободен — накопленное, затем `# пропущено <N> Б`, если было. Так после `pio run -t upload` и
  `pio device monitor` видны итог сеанса и первые строки платы, хотя между ними порт закрыт.
- `reset` — импульс NRST 10 мс без SWD, после него NRST отпущен; от чипа не зависит. Он же
  запас, если первые строки всё-таки пропали.

### 11. Команды и вывод

| Команда | Что делает |
|---|---|
| `help` | список команд; выводится и при старте вместе с выбранным чипом |
| `chip [имя]` | выбрать чип и запомнить; без имени — выбранный и список поддержанных |
| `info` | способ подключения, `IDCODE`, идентификатор чипа, UID, частота HSI, совпадают ли регистры таймингов с заводскими; вне сеанса gdb — свой короткий сеанс, плата перезапускается |
| `reset` | перезапуск платы |
| `baud <N>` | скорость лога |
| `swdp_scan` | только через `monitor`: начать сеанс и назвать чип строкой `1 py32f002b`. Строкой в мониторе — отказ: такой сеанс ничто бы не закрыло |

- Строкой в текстовом режиме и через `monitor` — один обработчик и одинаковые строки. Во время
  сеанса gdb `chip` и `reset` отвечают «идёт сеанс».
- Строки о подключении сеанс всегда выводит в порт; если команда пришла из gdb — ещё и в gdb.
- Адрес вне памяти чипа в `vFlashErase` или `vFlashWrite` — строки `# адрес вне памяти чипа: …`
  и `# итог: ошибка, …` сразу: после ошибки gdb `vFlashDone` не шлёт.
- Каждый шаг записи — строка `# ` со временем в мс:
  `# SWD: под сбросом, IDCODE 0x0bc11477, 3 мс` → `# HSI 24 МГц, тайминги заводские` →
  `# flash: 10 стр., 70 мс, стирание 3,4–3,6 мс, запись 1,0–1,1 мс` → `# otp: записано, 7 мс` →
  `# сверка: 25 мс` → `# итог: ок, 120 мс`. Строки сеанса gdb идут в порт, когда он свободен
  (§10).
- Числа в hex — с `0x`.

## Risks / Trade-offs

- **[Чип не отвечает ни под сбросом, ни в первые 50 мс после]** → сначала исключить провода: тот
  же ESP32-S3 с esp-usb-bridge и pyOCD (§3). Если провода целы — ключ питания платы от оснастки и
  вход сразу при подаче питания. Исход записать в tasks.
- **[Встречные выходы на ногах SWD]** → резисторы, наименьшая сила выхода, ноги отпущены вне
  сеанса (§2, §5).
- **[Неверное питание платы]** → 3,0–3,6 В или преобразователь уровней (Ограничения).
- **[SWD сбоит на проводах]** → снизить частоту константой; короткие провода, общий GND.
- **[Замок OTP навсегда]** → три рубежа: правило в `core/plan` с тестами на ПК до первой пробы
  на плате (задача 2.2), отказ «записать единицу» у PY32F002B (§6), проверка стирания OTP перед
  записью (§7). Обрыв питания посреди записи OTP — совет в Ограничениях и README.
- **[Аппаратный IWDG сбросит чип посреди записи]** → `DBGEN` и проверка `DBG_IWDG_STOP` до
  записи, перезарядка сторожа после каждой страницы, отметка `S_RESET_ST` (§3, §4, §8).
- **[Неверные тайминги flash]** → проверка HSI 24 МГц, загрузка заводских значений для 24 МГц
  перед записью, время каждой операции против DS, сверка с PR #2000 Black Magic Debug (§4, §6,
  §7; задачи 1.1, 6.2, 8.6).
- **[Свежий чип отвергнут как «HSI не 24 МГц»]** → поле частоты сравнивается с заводским словом
  кристалла, а не с подписью в RM (Context); в отказе и в `info` — оба значения. Если отказ всё
  же ложный, правило сменить на предупреждение (задача 8.2).
- **[`EOP` у PY32F002B ненадёжен]** → Puya его после страницы не проверяет (Context). Если на
  плате `EOP` не приходит, а сверка проходит — стоп по `EOP` убрать и опираться на сверку
  (задача 8.4).
- **[Повторная разблокировка запрёт `FLASH_CR`]** → разблокировать только при `LOCK` = 1,
  запирать после каждой записи (§6, §7); два `load` в одном сеансе — задача 8.4.
- **[Образ одного чипа зальют в другой]** → чип называется аргументом и сверяется по
  идентификатору до записи (§4, §6).
- **[PlatformIO покажет успех при провале]** → `vKill` отвечает `OK` только после удачной записи
  (§9); на заглушке это даёт код 1 и при `Load failed`. На плате — задачи 8.4 и 8.5.
- **[Вывод при открытии порта сорвёт подключение gdb]** → ничего не выводить, пока не ясно, кто
  открыл порт (§9); тест на ПК (задача 4.3) и задача 8.3.
- **[Другая версия gdb шлёт другие пакеты]** → незнакомый пакет получает пустой ответ, и gdb
  считает его неподдержанным. Тесты прогоняют записанные последовательности; с новым тулчейном
  PlatformIO их записывают заново (задача 1.6).
- **[Открытие порта не видно или перезагружает оснастку на Windows]** → DTR через
  `tud_cdc_n_get_line_state()`; без него первые строки после заливки теряются до открытия
  монитора, запас — `reset` (§10). Перезагрузка — выключить `reboot_enable` (§1). Проверяется
  задачей 8.3.
- **[Брошенный сеанс оставит плату остановленной]** → 60 с без пакетов, отметка в RTC-памяти
  (§5). Если оснастка потеряла питание, а плата нет — помогает `info` (Ограничения). Задача 8.5.
- **[Защищённая страница посреди образа]** → запись остановится на ней, часть страниц уже
  переписана (Ограничения). Снимать защиту — отдельный change, если понадобится.
- **[Описание чипа подогнано под PY32F002B]** → реализация одна, интерфейс введён по требованию
  владельца. Второй чип может потребовать FLM, настройку тактирования или единицу стирания в
  4 КБ. Тогда меняются действия в описании и, возможно, размер карты (§7). SWD, подключение,
  план, образ, протокол gdb и команды не меняются. Это и проверяет граница.
- **Не прячем за интерфейс GPIO, UART и USB ESP, и `port/` не гоняем на ПК.** Железо одно,
  вторая реализация не ожидается (А5, Галл). Решения о данных, порядок записи, режимы порта и
  пакеты gdb вынесены в `core/` и покрыты тестами. На плате проверяются только подключение,
  запись, USB и время.
- **Не вводим слой «источник образа»:** и gdb, и будущая страница говорят одним протоколом
  (§9).
- **Отказ от FLM для PY32F002B** (§3): в новой ревизии чипа с другим алгоритмом правится
