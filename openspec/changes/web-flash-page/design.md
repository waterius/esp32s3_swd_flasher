## Context

Зачем — `proposal.md`, что должно получиться — спеки `web-flash`, `swd-flash`, `gdb-server`.
Здесь только то, что задаёт способ.

- **Оснастка** (change `swd-flash-py32f002b`, design §1, §9, §10) — то, на что опирается
  страница:
  - один USB-порт, текстовый режим и режим gdb. Вывод идёт, только когда поднят DTR: при
    опущенном DTR оснастка в порт не пишет вовсе;
  - кто открыл порт: первый входящий `+` или `$` — gdb; другой байт — человек; 250 мс тишины —
    монитор, вывод разрешён. Верный пакет переводит в режим gdb и из текстового режима;
  - после ответа на `vKill` или `D` вывод ждёт закрытия порта или байта от человека;
  - карта памяти — `qXfer:memory-map:read`, из описания чипа; `PacketSize = 0x1000`;
  - `vKill` — `OK` только после удачной записи (и, с этим change'ем, удачного `erase`), `D` —
    всегда `OK`; без сеанса `m`, `vFlash*` — `E01`;
  - свои строки — `# ` с начала строки, итог сеанса — `# итог: ок, <мс> мс` или
    `# итог: ошибка, <причина>`.
- **Перезагрузка оснастки в загрузчик ESP** (Arduino-ESP32 3.3.12, `USBCDC.cpp`): линии
  (DTR, RTS) по шагам (0,1) → (1,1) → (1,0) → (0,0) или скорость 1 200 в line coding. Переходы
  (0,0) ↔ (1,1) её не запускают.
- **Web Serial:** есть в Chrome и Edge на компьютере (с версии 89), нет в Firefox и Safari.
  Нужен защищённый источник: HTTPS или `localhost`. `navigator.serial.requestPort({filters})`
  спрашивает человека один раз, дальше `getPorts()` отдаёт разрешённые порты. `open({baudRate})`,
  `setSignals({dataTerminalReady, requestToSend})`, чтение и запись — потоками; перед `close()`
  читатель и писатель отпускаются. Поднимает ли Chrome DTR сам при `open()` на каждой ОС — не
  проверено, поэтому страница поднимает его явно.
- **GitHub Pages** на бесплатном тарифе — только для публичного репозитория (у организации
  `waterius` тариф free, 2026-11-12). Источник «Deploy from a branch» — корень или `/docs`
  ветки; адрес — `https://waterius.github.io/esp32s3_swd_flasher/`, HTTPS.
- **Полное стирание PY32F002B** (RM §4.2.3.4, §4.2.1; `FlashPrg.c`, `EraseChip`):
  - стирает всю основную flash, информационную область (в том числе USER OTP) не трогает;
  - порядок: `BSY` свободен → ключи `KEYR` → `FLASH_CR |= MER | EOPIE` → запись любого слова в
    основную flash → ожидание `BSY` → `EOP`, сбросить; затем снять `MER`;
  - при включённой защите записи или Load flash стирания нет, ставится `WRPERR`;
  - время — как у страницы: 3,5 мс, наибольшее 5,0 мс (DS табл. 5-15, строка «Page/sector/mass
    erase»); в описании чипа — своё поле `main_erase_max_us`, у другого чипа оно может быть больше.

## Goals / Non-Goals

**Goals:**
- Одна страница без сборки и без внешних файлов: открыл ссылку — прошил.
- Тот же протокол и те же правила записи, что у PlatformIO: страница ничего не решает за
  оснастку, кроме проверки файлов до сеанса.
- Разговор с оснасткой — модулем, который страница изделия берёт копией.
- Разбор файлов, кадры протокола и порядок сеанса проверяются тестами на ПК.

**Non-Goals:**
- Установка прошивки самой оснастки из браузера.
- Данные для каждой платы, сервер изделия, учёт плат.
- Телефоны, Firefox, Safari.
- Сохранение лога и прочитанной памяти в файл.

## Ограничения, заметные человеку

- **Только Chrome или Edge на компьютере.** В остальных браузерах страница так и скажет.
- **Порт открывает одна программа.** Перед страницей закрыть `pio device monitor` и gdb: на
  Windows порт иначе не откроется, на macOS программы делили бы байты.
- **Файл с диска** (`file://`) не обещаем: Web Serial требует защищённого источника. Работает
  страница с GitHub Pages или с `localhost` (`python3 -m http.server -d docs`).
- **`info` и чтение памяти перезапускают плату:** это короткие сеансы SWD.
- **Лог на странице** — последние 5 000 строк; перезагрузка страницы его теряет.
- **Обрыв USB посреди записи** оставляет плату недописанной — прошить ещё раз. Брошенный сеанс
  оснастка завершит сама.
- **Полное стирание без файлов** страница не делает: для этого — команда `erase` в строке
  команд.

## Decisions

### 1. Web Serial и протокол gdb, а не WebUSB и CMSIS-DAP

- Страница говорит с оснасткой тем же протоколом gdb, что PlatformIO (swd-flash design §9).
  Правила записи, OTP и отказы — в оснастке, одни на всех. Прошивка оснастки ради страницы не
  меняется, кроме команды `erase` (§8).
- **Отвергнуто: WebUSB и CMSIS-DAP** (DAP.js, FreeOCD WebDebugger). Оснастке нужна была бы
  вторая прошивка, а порядок записи, правила OTP и подключение к спящему чипу — заново на
  JavaScript. Путь PlatformIO при этом пропал бы.
- **Отвергнуто: текстовые команды для записи.** Второй протокол для программ (swd-flash
  design §9).

### 2. Без сборки и без внешних файлов

- `docs/index.html`, `docs/style.css`, `docs/app.js` и модули `docs/lib/*.js` — обычные
  ES-модули, браузер грузит их как есть. Ни фреймворка, ни сборщика, ни CDN.
- Так страницу видно целиком в исходниках, она не делает сетевых запросов кроме своих файлов
  (спека `web-flash`), а страница изделия копирует модули без инструментов.
- Тесты — `test/web/*.test.mjs`, `node --test test/web`, вне `docs/`, чтобы не публиковаться.
- **Отвергнуто: фреймворк и сборка** — зависимость и шаг сборки ради пяти кнопок (А5).

### 3. Модули и зависимости

| `docs/lib/image.js` | образ из нескольких файлов, противоречия с именами обоих файлов, проверку по карте памяти, блоки для `vFlashErase`, куски для `vFlashWrite` | `ihex.js` | порт |

- Ни один модуль в `docs/lib/` не знает об изделиях: имён, раскладок и форматов данных там нет.

### 4. Протокол «порт оснастки»

Внешняя зависимость — Web Serial. Страница изделия может взять другой способ (другой браузерный
API, мост в настольном приложении), поэтому `flasher.js` получает порт протоколом:

- **протокол** — «порт оснастки», в `flasher.js` (описание JSDoc): `open()` — открыть и
  поднять линии; `close()`; `write(bytes)`; `onData(callback)` — принятые байты; `onClose(callback)`
  — порт пропал (выдернули USB);
- **реализация** — `webserial.js`: `requestPort` с фильтром `usbVendorId: 0x303A`,
  `open({baudRate: 115200})`, затем `setSignals({dataTerminalReady: true, requestToSend: true})`
  — переход (0,0) → (1,1), он не перезагружает оснастку (Context). Скорость 1 200 и другие
  сочетания линий не задаются. Закрытие отпускает читателя и писателя и опускает линии;
- **точка сборки** — `app.js`, один порт на страницу;
- **контракт на краях** — повторный `open()` — ошибка; запись в закрытый порт — ошибка; порт
  занят другой программой — ошибка с текстом «порт занят: закройте монитор и gdb»;
- **в тестах** — `test/web/fake_flasher.mjs`: поддельная оснастка по таблице пакетов
  swd-flash design §9 и текстовому режиму, с поддельным чипом в памяти.

### 5. Сеанс записи

Порт открыт один раз и остаётся открытым: между сеансами в нём идёт лог (§6).

1. Карта памяти: `+`, `$qSupported…`, `QStartNoAckMode`, `!`, `qXfer:memory-map:read` по
   кускам. Первый верный пакет переводит оснастку в режим gdb (Context). Оснастка отвечает
   картой из описания чипа, к плате не подключаясь.
2. Образ: `image.js` разбирает выбранные файлы и сверяет с картой. Отказ — `D`, затем перевод
   строки (§6), к плате оснастка не подключалась.
3. `qRcmd swdp_scan`, `vAttach;1` — сеанс SWD. Ошибка — `D`, итог страницы «ошибка» со
   строками оснастки.
4. Отмечено полное стирание — `qRcmd erase`.
5. `vFlashErase` по блокам карты, в которые попал хотя бы байт образа (как gdb); `vFlashWrite`
   кусками не больше `PacketSize − 64` после экранирования; ход — по отправленным байтам;
   `vFlashDone`.
6. `vKill;1` — оснастка завершает сеанс и запускает плату. `E01` — значит, запись не удалась
   (Context).
7. Перевод строки `\n` — «байт от человека»: оснастка возвращается в текстовый режим и выводит
   накопленное — строки сеанса, итог, лог платы. Пустую строку оснастка пропускает (спека
   `gdb-server`). Итог страницы — строка `# итог:` оснастки.

- **Подтверждения** страница не ждёт и не перепосылает пакеты: ответ — следующий пакет с верной
  суммой, байты до `$` пропускаются. Так лог, который шёл до перехода в режим gdb, не мешает.
- **Сроки ответов:** обычный пакет — 2 с; `qRcmd erase` — 10 с, как `vFlashDone`: оснастка
  отвечает после стирания и чтения всей основной flash по SWD, а у чипа побольше или на медленном
  SWD это дольше 2 с. Вышел срок — «оснастка не отвечает», порт закрывается: оснастка увидит
  падение DTR и завершит сеанс. Другая ошибка посреди сеанса (не записался пакет, пустая карта) —
  `D` и перевод строки, как в конце обычного сеанса, порт остаётся открытым.
- **Строки, которые страница разбирает** (контракт с оснасткой, А4): `# чип: <имя>`,
  `# чип не выбран`, `# поддержаны: <имя>, …`, `# итог: ок…`, `# итог: ошибка…`. Остальные
  строки страница показывает как есть.

### 6. Лог и команды

- После `open()` страница ничего не шлёт: через 250 мс оснастка решает, что на том конце
  монитор, и выводит накопленное и живой лог (Context).
- Строки делятся по LF. Строки `# ` — оснастки, выделены; остальные — лог платы.
- Команда из поля ввода уходит строкой с `\n`. Сразу после подключения страница шлёт `chip` и
  показывает ответ: выбранный чип и список для выбора.
- Во время сеанса записи (§5) поле команд недоступно.

### 7. Чтение памяти

- Области — из карты памяти; можно ввести адрес и длину. Сеанс как в §5, шаги 1 и 3, затем `m`
  кусками по `0x400` Б (ответ в hex вдвое длиннее, укладывается в `PacketSize`), затем `D` —
  не `vKill`, чтобы чтение без записи не дало ошибки (Context), и перевод строки.
- Вывод — строки по 16 Б: адрес с `0x` и байты в hex.

### 8. Команда `erase` в оснастке

- **Описание чипа** получает отметку области «основная»: у `py32f002b` — `flash`. Действие чипа
  «стереть основное» — у PY32F002B по RM §4.2.3.4 (Context), после «разблокировать», то есть с
  загруженными таймингами (swd-flash design §6); `BSY` с пределом 50 мс; `WRPERR` — отказ
  «полное стирание невозможно: защита записи».
- **`core/write`** получает шаг «стереть основное»: стереть, затем прочитать всю основную
  область и проверить `0xFF` — первый другой байт — `ошибка` с адресом. Тест на поддельном
  чипе, в том числе с `WRPERR`. Чтение 24 КБ при 1 МГц SWD — около 0,3 с.
- **Команда:** строкой и через `monitor`; в сеансе gdb — в нём, вне сеанса — свой короткий
  сеанс с перезапуском платы. Удачное `erase` отмечает сеанс удачной записью для `vKill`.
- Последующий `vFlashErase` снова стирает страницы образа — лишние 3,5 мс на страницу,
  оптимизацию не делаем (А5).

### 9. Публикация

- GitHub Pages, «Deploy from a branch»: `master`, папка `/docs`. Включает владелец после того,
  как репозиторий станет публичным. Сборки и GitHub Actions нет.
- Ссылка на страницу — в `README.md`, в начале.

### 10. Страница изделия

- Берёт копию `docs/lib/` с метки версии этого репозитория и строит свой экран поверх
  `flasher.js`: свои данные для USER OTP, свой учёт. Описание `flasher.js` для неё — в
  `README.md`.
- Страница прошивки от страниц изделий не зависит и о них не знает.

### 11. Язык

Интерфейс — русский. Все надписи — в одном объекте в `app.js`, чтобы позже добавить английский
(открытый вопрос в business.md).

## Risks / Trade-offs

- **[Chrome не поднимает DTR сам]** → страница поднимает DTR и RTS явно (§4); проверяется на
  Windows и macOS (задача 7.1).
- **[Лог платы содержит `$…#xx` с верной суммой как раз в начале сеанса]** → страница примет
  его за ответ. Вероятность мала: оснастка перестаёт выводить лог с первым пакетом. Не
  защищаемся.
- **[Перевод строки не освободит вывод]** → запас: закрыть и открыть порт — оснастка увидит
  падение DTR (§4).
- **[Страница изделия разойдётся со своей копией `lib/`]** → метка версии и описание в README;
  отдельную библиотеку с версиями не делаем, пока страница изделия одна (А5).
- **[GitHub Pages недоступен]** → та же страница с `localhost`.
- **Не прячем за интерфейс DOM и `app.js`:** экран один, второй реализации нет (А5). Под
  интерфейс уходит только порт — его подменяет и тест, и страница изделия (§4).

## Migration Plan

Переносить нечего: страницы не было. Архивировать после `swd-flash-py32f002b`: дельты `swd-flash`
и `gdb-server` правят его требования (proposal).

## Отступления при реализации

- **Запуск тестов страницы** — `node --test "test/web/*.test.mjs"`, Node 22+: Node 22 и новее
  каталог аргументом `--test` не принимают, только шаблон (§2).
- **Итог erase для vKill:** `gdb::Target.command` возвращает `gdb::Outcome` (`None`, `WriteOk`,
  `WriteFailed`), `commands::run` — тоже; так сервер gdb отмечает удачное или неудачное `erase`, не
  зная команд (§8). У хозяина команд — функция `erase`.
- **Строки erase в сеансе gdb** идут и в вывод оснастки, и пакетами `O` — как `info`. Пакеты `O`
  страница не показывает (те же строки придут после сеанса), но по строке `# итог:` из них решает,
  продолжать ли запись после `erase` (§5, шаг 4).
- **Итог страницы** — ошибка, если `vKill` ответил `E01` или хоть одна строка `# итог: ошибка`;
  причина — из последней такой строки, а без неё — последняя строка `# ` оснастки или своя. Строк
  `# итог:` за сеанс может быть две: стирание и запись. Ждёт их страница до 2 с (§5, шаг 7).
- **Карта памяти** запрашивается и сразу после подключения, без подключения к плате, — для списка
  областей чтения (§7).
- **Расписки покрытия** — `test/spec_coverage/spec_coverage_data.py` (там живёт `TRACKED` этого
  репозитория), протокол — `dev/board-checks-web.md`.
- **`<link rel="icon" href="data:,">`** — иначе браузер сам запрашивает `favicon.ico` (спека
  `web-flash`, «Нет сетевых запросов»).
